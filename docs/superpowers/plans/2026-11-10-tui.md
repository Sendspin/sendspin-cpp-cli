# `sendspin-cli tui` Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add a `sendspin-cli tui` subcommand. It attaches to the running player over the control
socket, takes over the screen with the code while a server pairs, and otherwise shows what is
playing and drives playback.

**Architecture:** The work comes in three groups.
- **Player side (Tasks 1-4).** The player learns to:
  - remember how the last pairing attempt ended;
  - report the album, the codec and the group name;
  - take this player's own volume and mute as commands;
  - answer a machine-readable `status-kv`.
- **Client side (Task 5).** A structured exchange function, so a long-lived client can talk to
  the socket.
- **The TUI itself (Tasks 6-8).** It is split into:
  - a pure model in `sendspin-cli-core` (no FTXUI), which is unit-tested;
  - a thin FTXUI view, linked into the executable only.

**Tech Stack:** C++20, CMake with FetchContent, FTXUI v7.0.3, GoogleTest. The control socket
protocol is unchanged.

**Spec:** `docs/superpowers/specs/2026-11-10-tui-design.md`. Read it before starting; this plan
argues from it.

**Branch:** implement on `feat/tui`, cut from `docs/tui-design` so the spec and this plan
travel with the code.

## Global Constraints

- **Nothing about the control socket protocol changes:** one command per connection; the
  first reply line is `ok` or `error <kind>: <reason>`; the payload follows `ok`.
- **No new main-loop threads.** Everything the dispatcher reads stays on the main loop. The TUI
  is a separate process.
- **Existing `status` text keeps every line it has, with the same wording.** New information
  arrives only as new lines.
- **Add new `ControlCommand` values before `Delay`.** `Delay` stays last
  (`EveryCommandInTheEnumHasARow` walks the enum up to it).
- **Builds:**
  - Windows: clang-cl with `-Werror` (`SENDSPIN_CLI_WERROR=ON`) and the static CRT.
  - Every source file: `scripts/format.sh --check` passes (clang-format 20.1.8).
- **FTXUI is pinned to tag `v7.0.3`, commit `f921fad208912747c17d129a8ef75ec7624b6eec`.** Pin
  it by that SHA, without `GIT_SHALLOW`, matching the sendspin-cpp pin.
- **No FTXUI header is included from any file in `sendspin-cli-core`.** Tests link only core.
- **The pairing token is never logged and never shown until `p` is pressed.**
- **Hand-written files stay ASCII**, except where the box-drawing glyphs for the large digits
  need UTF-8 in `src/tui_model.cpp`.

## Review Focus

1. **Metadata with newlines or `=` in it.** A title such as `a=b` plus a newline plus `c` must
   reach the TUI as `a=b c`, not split a key. (Task 4 test
   `StatusKv.ANewlineInAValueCannotStartAKey`.)
2. **A TUI opened after a pairing already ended** must not replay "Paired with ..." at launch.
   Only an attempt that ends *while it watches* takes over. (Task 6 test
   `TuiModel.AnOutcomeFromBeforeLaunchIsNotReplayed`.)
3. **The player restarts while the TUI is open.** The socket vanishes, the TUI shows the
   no-player screen, then reattaches. The restarted player's attempt counter starts at 0
   again, so the baseline is reset on reattach. (Task 6 test
   `TuiModel.ReattachingResetsThePairingBaseline`.)
4. **A player older than the TUI** refuses `status-kv` as an unknown subcommand. The TUI must
   say "this player is older than this TUI -- update it" rather than loop on an error. (Task 6
   test `TuiModel.AnOlderPlayerIsNamedAsSuch`.)
5. **A small SSH terminal** (40x12). The code must still be readable: the large digits fall
   back to a spaced plain code when they don't fit the width. (Task 6 test
   `TuiModel.ThePairingCodeFallsBackToPlainTextWhenNarrow`.)

**Interfaces:**
- Produces:

  ```cpp
  enum class PairingOutcome : uint8_t { None, Paired, Failed, Abandoned };
  struct PairingAttemptResult {
      uint32_t attempt{0};          ///< 1-based number of the attempt that ended; 0 = none yet
      std::string server_id;
      PairingOutcome outcome{PairingOutcome::None};
      std::string reason;           ///< set for Failed only
  };
  class PairingTracker {  // main loop only; no logging, no library types
  public:
      void started(const std::string& server_id);
      void succeeded(const std::string& server_id);
      void failed(const std::string& server_id, const std::string& reason);
      void code_shown(const std::string& code);
      void code_cleared();
      void window_opened();
      void window_closed();
      void connection_ended();  ///< a new handshake, or the connection dropped
      const std::string& in_progress_server_id() const;  ///< empty when no attempt is open
      const std::string& code() const;
      bool window_open() const;
      const PairingAttemptResult& last() const;
  };
  ```
- `StatusSnapshot` gains `PairingAttemptResult last_pairing{};`.

The library's order (checked in sendspin-cpp `b0fcf5bb`) determines the semantics:
- **Success:** the code is cleared *before* `on_pairing_succeeded`.
- **Failure:** `on_pairing_failed` comes first, then the clear.
- **A dropped connection:** only the clear.

So `code_cleared()` and `window_closed()` never end an attempt. Only `succeeded`, `failed`,
`connection_ended`, or a new `started` while one is open (recorded as Abandoned) does.

**Interfaces:**
- Table row: `{"status-kv", StatusKv, 0, nullptr, "Status as key=value lines, for scripts and the TUI"}`.
  It is answered locally, like `status`.
- The format, which the wiki section reproduces:
  - one `key=value` per line, in a fixed order, the first line `version=1`;
  - the value runs to the end of the line; any `\r` or `\n` inside a value becomes a space;
  - booleans are `0`/`1`; an unknown or absent value is empty.
  - Keys, in order: `version name client_id connected server_name server_id trust
    paired_servers pairing_server_id pairing_code pairing_window last_pairing_attempt
    last_pairing_outcome last_pairing_server_id last_pairing_reason state streaming codec
    sample_rate channels bit_depth title artist album position_ms duration_ms
    group_state_known group_volume group_muted group_name repeat shuffle player_volume
    player_muted player_volume_source output_delay_ms output input input_streaming`.
  - Value vocabularies:
    - `trust`: `paired`, `unpaired`, or empty while not connected;
    - `last_pairing_outcome`: empty, `paired`, `failed` or `abandoned`;
    - `state`: the same word the human `state:` line prints;
    - `repeat`: `off`, `one` or `all`;
    - `player_volume_source`: `default`, `restored`, `server`, `fixed`, `hardware` or
      `local`;
    - `codec`: `codec_name()` (Task 2).
  - **No timestamp key.** The client times a position by when it received the reply. The
    socket answers within one 10 ms tick, so that is accurate enough to interpolate from.
    *(This is a plan decision against the spec's "with the time they were taken".)*
- Produces:
  ```cpp
  std::string format_status_kv(const StatusSnapshot& snapshot);
  /// The parsed form the TUI reads. Every field defaults to "unknown".
  struct PlayerView { /* one member per key above, typed: std::string, bool,
                         std::optional<uint32_t> for position/duration, uint8_t volumes,
                         uint32_t last_pairing_attempt, ... */ };
  /// Unknown keys are ignored; missing keys keep their defaults. False only when `version`
  /// is missing or not 1.
  bool parse_status_kv(const std::string& payload, PlayerView& out);
  ```

### Task 6: The TUI model, with no UI library

**Files:**
- Create: `src/tui_model.h`, `src/tui_model.cpp` (in `sendspin-cli-core`)
- Test: `tests/tui_model_test.cpp` (new)

**Interfaces:**
- Consumes: `PlayerView`, `parse_status_kv` (Task 4); `ControlExchange` (Task 5);
  `ControlRequest` and `ControlCommand` (`control.h`).
- Produces:
  ```cpp
  enum class TuiScreen { NoPlayer, Denied, PlayerTooOld, Main, PairingCode, PairingConfirm,
                         PairingOutcome };
  enum class TuiKey { Space, Left, Right, Up, Down, LeftBracket, RightBracket, MuteSelf,
                      MuteGroup, Repeat, Shuffle, Switch, DelayDown, DelayUp, Token, Yes, No,
                      Quit };
  class TuiModel {
  public:
      /// Feed every status-kv poll. `now_ms` is a monotonic clock.
      void on_status(const ControlExchange& reply, int64_t now_ms);
      /// Feed the reply to a request the TUI sent; failures become a notice.
      void on_command_reply(const ControlExchange& reply, int64_t now_ms);
      void on_token(const ControlExchange& reply);  ///< the `pair-token` reply
      TuiScreen screen(int64_t now_ms) const;
      /// The request a key sends, or nullopt (Quit, Token, and keys that make no sense now).
      std::optional<ControlRequest> request_for(TuiKey key) const;
      void toggle_token();                  ///< `p`: show or hide; the view asks for it once
      bool wants_token() const;             ///< shown and not yet fetched
      const std::optional<std::string>& token() const;
      const PlayerView& view() const;
      std::optional<uint32_t> position_ms(int64_t now_ms) const;  ///< interpolated while playing
      std::string notice(int64_t now_ms) const;  ///< empty when none is current
      std::string outcome_text() const;          ///< for PairingOutcome
      std::string no_player_reason() const;      ///< for NoPlayer and Denied
  };
  /// The code in 5-row block digits, or the code spaced out on one row when 6*n-1 > width.
  std::vector<std::string> pairing_code_lines(const std::string& code, int width);
  ```
- The rules, which the tests pin:
  - **Screens.**
    - A `NoDaemon` reply gives `NoPlayer`, or `Denied` when `denied` is set.
    - A `Usage` reply to `status-kv` (an older player has no such subcommand) gives
      `PlayerTooOld`.
    - Otherwise, the first match of:
      - `PairingConfirm` when `pairing_window`;
      - `PairingCode` when `pairing_code` is non-empty, or `pairing_server_id` is non-empty
        (the outcome is awaited; the view shows "Confirming with the server...");
      - `PairingOutcome` for 3000 ms after a new outcome;
      - `Main`.
  - **The baseline.** The first successful poll after any non-attached state records
    `last_pairing_attempt` as the baseline. Only a value above it starts `PairingOutcome`.
  - **Outcome text.**
    - "Paired with <name>", where the name is `server_name` when `last_pairing_server_id`
      equals `server_id`, otherwise the first 12 characters of the id plus "...".
    - Failed: "Pairing failed: <reason>".
    - Abandoned: "The server stopped pairing".
  - **Key mapping.**
    - Space: `Pause` when `state` is `playing`, else `Play`.
    - Up/Down: `PlayerVolume` with `player_volume` +/- 5, clamped 0-100.
    - `]`/`[`: `Volume` with `group_volume` +/- 5, clamped 0-100.
    - `m`: `PlayerMute` with `!player_muted`. `M`: `Mute` with `!group_muted`.
    - `r`: `Repeat` with off to all, all to one, one to off.
    - `x`: `Shuffle` with `!shuffle`. `g`: `Switch`.
    - `,`/`.`: `Delay` with `output_delay_ms` -/+ 10, clamped 0-5000.
    - Yes/No: `Pair` with confirm true/false, only on `PairingConfirm`; otherwise nullopt.
  - **Notices.** A command reply that isn't Ok shows for 3000 ms:
    - `Unsupported`: "The server doesn't offer that";
    - `NotConnected`: "No server is connected";
    - anything else: the reason.
